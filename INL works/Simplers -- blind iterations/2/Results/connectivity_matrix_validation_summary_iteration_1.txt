Connectivity matrix validation summary - Document 2, Iteration 1

Ground truth normalization:
The GT file is an edge list, so it was normalized into an undirected set of component-to-component edges before validation. The extracted CSV files were adjacency matrices and were normalized into the same undirected edge-set format. Only Diego/Jennifer round matrix files were evaluated; final_connectivity_matrix.csv was not included because it is not tied to an extractor-round row name.

GT after normalization: 58 undirected edges across 55 component names.

Main reason the scores were not perfect:
The non-perfect score was caused by imperfect connectivity/edge discovery, not by component naming. All GT component names were present exactly in every extracted round matrix, there were no extra non-GT matrix nodes, and there were no false positives. The only drop came from two GT edges that were missing in every evaluated round.

Missing GT edges causing the drop:
- PAN-RPS-A -- RELAY-K12A
- PAN-RPS-B -- RELAY-K12B

What was not responsible:
- Component names were not wrong or close-but-imperfect; every GT component name appeared exactly.
- No GT components were missing from the extracted matrices.
- No extra intermediate nodes were inserted into the extracted matrices.
- No false-positive extracted edges were found.

Examples causing the drop:
- PAN-RPS-A and RELAY-K12A are both present as component names, but the GT edge PAN-RPS-A -- RELAY-K12A was not discovered.
- PAN-RPS-B and RELAY-K12B are both present as component names, but the GT edge PAN-RPS-B -- RELAY-K12B was not discovered.

Counterfactual performance:
Because there were no extra nodes or false positives, there is nothing to remove from the extraction. Removing non-GT items would leave the score unchanged. If the two missing relay-to-RPS-panel edges had been added, every round would have reached a perfect score.
